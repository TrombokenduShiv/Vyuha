1. Document Control, Engineering Scope and Non-Negotiables
This TRD operationalizes the Vyuha 2.0 PRD into buildable modules, exact interfaces, ownership boundaries, test gates and a time-boxed hackathon execution plan. It is intentionally more implementation-oriented than the PRD: every deep-tech component is mapped to code, data, model artifacts, API contracts, fallback behavior, owner and acceptance test. The PRD remains the product-source-of-truth; this document is the engineering-source-of-truth for how the prototype is assembled.

1.1 Engineering invariants
Core edge inference shall work with network disabled after model/config bootstrap. Missing remote evidence is represented as MISSING/UNEVALUATED, never coerced to “safe.”
The SDK shall never ingest call audio, screen pixels, private chat text, UPI PIN, OTP, raw contact book or arbitrary app content for the MVP.
The graph service shall return only a short-lived signed beneficiary-risk assertion, not raw neighbor identities or a portable mule graph.
Intervention severity shall be determined by fused evidence plus uncertainty. A single weak signal such as an active call cannot independently produce a high-severity decision.
Any warning/action visible to the user must be reproducible from a stable action ID, reason codes, model version and policy version.
Production architecture and hackathon shortcuts must be labelled separately. A simulated signal is acceptable for demo only when the platform capability cannot be provisioned in 24 hours.

1.2 Source and research basis
This TRD inherits the PRD research basis: Heterogeneous Graph Transformer (HGT), Temporal Graph Networks (TGN), TGAT, CARE-GNN, sparse Mixture-of-Experts, POMDP-style belief-state reasoning, conformal prediction, conservative contextual bandits, offline RL and federated learning research. It also follows current Android platform constraints: Play Integrity app-access-risk can identify capture/control/overlay capability but is a server-verified signal and can add hundreds of milliseconds; therefore it is treated as asynchronous augmentation rather than the sub-50 ms local critical path. ExecuTorch provides Android AAR/Kotlin-Java bindings and an XNNPACK backend suitable for a quantized local model bundle. [R7–R10, R19–R28]

Own final visual rehearsal: no dead buttons, no loading spinner dependence on internet, no broken responsive layout, and predictable transitions for screen recording/presentation.

4. Runtime Architecture and Trust Boundaries

Figure 1. Three-plane Vyuha architecture. Only Plane A is required for the offline critical path.
Plane A is the only component that must participate in the sub-50 ms local decision budget. Plane B can enrich risk with beneficiary-network evidence. Plane C trains and validates policy offline; it does not execute unrestricted learning on a live victim. The product must continue to function when Plane B is unavailable.
4.1 Runtime sequence

Figure 2. Local-first runtime decision flow with optional graph augmentation.
Host creates a `TransactionContext` before the user reaches final payment authorization and calls `startSession()`.
SDK captures bounded local features: transaction novelty, local baseline, communication state and any host/device-risk assertions already available.
Triage gate checks for clearly benign context. If safe-path criteria are met, the SDK emits PASS without user-visible UI.
Otherwise the Sparse Risk-MoE scores the session. The coercion belief state accumulates sequential evidence rather than treating one event as conclusive.
In parallel, the host/backend requests beneficiary risk. A valid signed `GraphRiskToken` is fused if it arrives before the decision deadline; otherwise graph state is UNKNOWN and the local path proceeds.
Conformal/selective uncertainty determines whether the model is confident enough for a stronger action or should abstain / use lower-cost friction.
Frozen policy selects one pre-approved action. The host UI renders it natively. Response events are returned to the current session and may trigger a second belief update.
Outcome is finalized, persisted locally as a privacy-minimal trace, and asynchronously uploaded if permitted.

6.3 Hot-path low-latency rules
Preallocate float/int buffers for the fixed feature vector and temporal event tensor. Reuse them per session; do not create maps or JSON during inference.
Normalize features using constants from `normalization.json` loaded once. Missing values have explicit missing-mask bits rather than NaN.
Model load occurs at SDK initialization or payment-screen entry, never after PIN/authorization button press.
Keep the local tensor shapes fixed. Example: static features `[1, 32]`, temporal events `[1, 8, 16]`, graph augmentation `[1, 8]` with `graph_missing=1` when absent.
Use a dedicated background dispatcher/executor for inference; UI thread only awaits the result and renders. Cancel stale session work when session closes.
Profile before adding C++. If feature packing + orchestration is <5 ms, remain in Kotlin. Add NDK complexity only if measurement shows a real bottleneck.
Log p50/p95 after at least 100 warm runs; do not use one successful run as the latency claim.

7. Sparse Risk-MoE Triage Gate — Trombokendu Ownership
The local model must justify the “Mixture of Experts” label technically. The implementation below uses a small sparse router that activates at most two experts for an elevated session. The fast gate can exit before expert execution for obvious benign traffic. The objective is not a gigantic MoE; it is conditional computation and interpretable expert separation under a mobile latency budget.

7.3 Training procedure
Generate a session dataset with scenario-family separation: benign routine payments, benign edge cases (new payee while on a call), ambiguous sessions and coercion-like sequences. Keep full scenario templates out of the validation/test split to reduce leakage.
Normalize continuous features on train split only. Persist means/scales and categorical mapping in the model bundle.
Train the experts + router end-to-end with binary cross-entropy and a small router load-balancing penalty so one expert does not absorb all traffic. Use class weighting/focal loss only if imbalance demands it.
Calibrate the fused probability on a chronological/held-out calibration set. Do not tune thresholds on the final test set.
Add expert ablations: device-only, transaction-only, baseline-only, temporal-only, full model. The demo can show that combined evidence matters.
Export a fixed-shape model using `torch.export`, lower with ExecuTorch XNNPACK and write `.pte`. Verify Python vs ExecuTorch output on golden vectors.
Quantize only after parity works. Compare float and quantized accuracy/calibration; retain float if quantization breaks the tiny model and still meets latency.
Package the `.pte` plus feature/calibration metadata and SHA-256. Aditya consumes only the bundle, never Python preprocessing code.

8. Coercion Belief State and Selective Uncertainty
Vyuha’s technical differentiation comes from treating coercion as a latent state that evolves across events. The phone does not “see coercion”; it sees weak contextual observations. The runtime therefore maintains a belief proxy and updates it as evidence accumulates. This is inspired by partially observable decision systems, but the hackathon implementation should remain small, transparent and testable.
8.1 Belief state implementation
Use a three-state conceptual model: AUTONOMOUS, UNCERTAIN and COERCED. For the prototype, maintain a scalar `b_t = P(coercion | observations)` using a recurrent log-odds update. Initialize weights from synthetic data and fit a logistic/recurrent calibration model rather than hand-tuning every coefficient.
Belief-state recurrence

8.2 Starter action envelopes — engineering defaults, not final policy

8.3 Conformal/selective prediction wrapper
Split a held-out calibration set after model training. Keep it separate from threshold tuning.
For binary classification, compute nonconformity `s = 1 - p_true` on the calibration examples.
Choose desired miscoverage α (for example 0.10 for prototype experimentation) and compute the finite-sample conformal quantile `q_hat`.
At runtime, form a prediction set containing class `c` when `1 - p_c <= q_hat`. `{SAFE}` is confident-safe, `{RISK}` is confident-risk, `{SAFE,RISK}` is ambiguous/abstain.
Feed prediction-set size and route entropy into the policy. Ambiguity should reduce confidence in aggressive action unless strong non-model evidence independently requires remediation.
Report empirical coverage on calibration/test data. Do not claim distribution-free protection against arbitrary future distribution shift; monitor drift.

9. Heterogeneous Spatio-Temporal GNN — Trombokendu Ownership

Figure 3. Heterogeneous temporal graph schema. “Spatial” refers to relational graph structure, not geographic coordinates.
The institution-side model answers a different question from the edge model: “Does the beneficiary participate in a suspicious evolving network topology?” The edge model estimates payer-side agency context; the ST-GNN estimates recipient/network risk. The fused system is stronger because either side can be low while the other is high.
9.1 Graph schema


9.2 Synthetic mule motif generator
Generate normal users with stable payee/merchant behavior, salary-like inflow and routine merchant payments.
Inject fan-in mule motif: many unrelated accounts send moderate amounts to one young account within a short interval.
Inject fan-out dispersal: one mule quickly sends funds to several downstream accounts.
Inject chain laundering: A→B→C→D with short time gaps and reduced amounts.
Inject device reuse: multiple nominally unrelated accounts appear on the same device within a compressed period.
Inject VPA churn: several young VPAs map to related accounts, then become dormant.
Inject delayed complaint nodes after suspicious transfer clusters, preserving realistic label delay.
Add camouflage edges to normal merchants and benign high-degree hubs so the model cannot equate degree with fraud.
Create hard negatives such as family transfers, rent collection and legitimate merchant fan-in.
Chronologically split data and hold out complete mule clusters from test so performance requires inductive generalization, not memorized node IDs.

11. Safety-Constrained Contextual Bandit, Offline RL and Agentic Digital Twin
The policy layer chooses friction, not “fraud truth.” This distinction is essential. The classifier estimates risk; the policy balances expected safety benefit against friction cost under hard safety constraints. Runtime learning is disabled. Exploration occurs only in synthetic/offline simulation.

14. Exact Build Sequence — Contracts First, Vertical Slice Before Polish
The implementation order below is dependency-driven. The team should resist starting four independent “cool modules” that cannot connect. The first end-to-end vertical slice uses fake model outputs, then each fake component is replaced one by one while the interface remains constant.
Step 0 — Repository + branch policy
Create monorepo, commit contracts/README, protect `main` by social rule: no direct breaking schema edits. Use feature branches `trombo/ml-*`, `aditya/sdk-*`, `alaukik/hci-*`, `sneha/ui-*`. Merge only at integration gates.
Step 1 — Freeze six contracts
TransactionContext, EventSnapshot, GraphRiskToken claims, RiskAssessment, InterventionDecision, WarningEvent. Export JSON fixtures and Kotlin/Pydantic copies.
Step 2 — Build a fake vertical slice
Android host opens a payment, fake SDK returns A3, warning UI runs cooldown, fake Safety Circle completes. This proves interface/UI flow before deep tech.
Step 3 — Build graph service with deterministic heuristic
Before ST-GNN trains, `/beneficiary-risk` returns fixture risk by beneficiary ID and signs token. Aditya can build signature verification immediately.
Step 4 — Build synthetic data generators
Trombokendu generates session trajectories + hetero graph. Freeze seeds and export train/val/test manifests.
Step 5 — Train ST-GNN baseline
Start with HGT snapshot or GraphSAGE to prove data pipeline. Then add temporal memory/encoding if stable. Publish model + service tests.
Step 6 — Train edge model
Train Triage/Risk-MoE + calibration. Export golden vectors and `.pte`.
Step 7 — Replace fake Android inference
Aditya integrates `.pte`; verify Python/Android parity; preserve public SDK API unchanged.
Step 8 — Implement belief + conformal + frozen policy
Trombokendu wires local risk + graph risk + response to final action. Alaukik approves action envelope.
Step 9 — Replace heuristic graph risk
Load ST-GNN in FastAPI; risk token now comes from model inference.
Step 10 — Harden warning flow
Sneha implements all states/error paths; Alaukik runs HCI checklist. No dead-end action.
Step 11 — Benchmarks + adversarial replay
Aditya measures latency; Trombokendu runs model metrics; Alaukik/Sneha run benign/high-risk user flow; team fixes only failures that affect demo/criteria.
Step 12 — Package and freeze
Publish AAR locally, assemble APK, save exact model/config hashes, start services from one script, run final demo twice from clean restart.

17. Demo Choreography and Presentation-Grade Engineering Trace
The demo should reveal deep technology only after the user story is obvious. A judge should first see a normal payment that is untouched, then a high-risk payment that changes state for specific reasons. The debug panel is the proof that the behavior comes from integrated models rather than a hard-coded warning.
17.1 Benign demo — 30–45 seconds
Open host payment screen with BENIGN_01 scenario.
Payee is known; amount inside normal percentile; no active communication. Graph token low-risk or graph missing.
Press “Continue to Pay.” SDK returns PASS. No warning renders.
Open engineering trace only after payment: show local p95 benchmark, fastPath=true, model hash. Close it quickly.
17.2 High-risk demo — 60–90 seconds
Switch to SCAM_01: large new-beneficiary payment while communication active and a controlling/capture-risk fixture is active.
Graph service receives beneficiary hash and returns a signed high-risk token because live synthetic graph shows fan-in/device-reuse motif.
Engineering trace shows router selected Device + Transaction experts; belief increases after graph fusion; conformal state is confident-risk or policy has corroborating evidence.

18. Failure Triage and Debug Playbook

18.1 Stop-the-line criteria
If the real model is not stable by G3, keep a smaller defensible model; never hard-code the final warning while claiming ST-GNN/MoE causality.
If app-access-risk cannot be provisioned, mark it SIMULATED and continue. Do not build a permission-abusive overlay/screen-scraper substitute.
If full TGN+HGT training is unstable, fall back to HGT with temporal aggregates and explain the production temporal-memory direction.
If the React dashboard threatens the Android vertical slice, cut it. The core demo is Android host + graph service + model trace.
If the bandit adds nondeterminism to the final demo, freeze the selected policy seed/coefficients and test actions deterministically.

21.1 Engineering evidence boundary
The cited research justifies why the selected architectures are technically plausible; it does not prove Vyuha’s eventual real-world accuracy, fairness or loss-prevention efficacy. The hackathon prototype validates system integration, model mechanics and measurable performance on synthetic/replay data. Production claims require institution-governed data, chronological evaluation, shadow deployment, human-factors studies and compliance/security review.
